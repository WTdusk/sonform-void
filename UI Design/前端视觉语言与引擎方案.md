# 物理建模音源系列：前端视觉语言与引擎方案

## 定稿（2026-11-17）

**手碟使用 Nodal（沙图振型），舌鼓使用 Calibre（刻度仪表）。** 两套设计都保留，Temper 不再采用（初版三方案稿归档在 `archive/visual-language-proposals-v1.html`）。

本目录文件：

- `series-ui-design.html`：当前设计稿。切换乐器时主题自动跟随乐器族（手碟 → Nodal，舌鼓 → Calibre），也可以临时切到另一套预览；小提琴仅作跨乐器族验证，主题未分配。

## 技术路线结论

技术上建议走 **JUCE WebView 前端**（HTML/CSS/JS 界面 + JUCE 参数桥接），理由和风险见下文。这样交互稿里的 token、组件和舞台渲染可以直接演进为产品代码，主题切换就是换一组 CSS 变量。

## 参考案例与可借鉴之处

Audio Modeling 的 SWAM 是最接近“建模音源系列”的先例：铜管、木管、弦乐三套不同的引擎共用同一个 v3 界面布局（主控、表现力、演奏模式、音色、音高、高级设置、控制器映射），而且产品第一次打开时会引导用户映射表情控制器，因为建模乐器只按键往往不能得到好声音。对我们的启示是：系列统一的是界面骨架和交互词汇，不是引擎；这与 `plugin/README.md` 里“统一的是产品入口和前端，而非各型号的物理参数或算法”完全一致。

AAS Chromaphone 3 把界面分成 Home（演奏）、Browser（音色库）、Editor（参数）三个视图，并直接用“激励器 + 共鸣体”的物理结构组织参数。我们的骨架借用了这一点：左栏是激励（手、槌、弓、气息），右栏是共鸣体与空间，所有乐器族都能落进这两个角色里。

Pianoteq 8 是“一个外壳、多种乐器”的另一个成功例子，它的改版重点是可读性和乐器/场景的清晰呈现。Anukari 则走到另一个极端，把 3D 物理模型本身当作主界面，用户直接看到并编辑质量块和弹簧。我们取中间位置：中央舞台显示乐器的可演奏表面和它的振动状态，但不把建模参数全部暴露出来。

## 共用骨架

三套方案用的是同一个骨架，这也是前端引擎要固化的部分：

```
┌ 顶栏：系列标识 │ 乐器族 + 型号选择 │ 预设 │ 输出电平 ┐
├ 左栏：激励 ────┬──── 中央舞台 ────┬─ 右栏：共鸣体与空间 ┤
│ 奏法列表       │ 可演奏表面        │ 阻尼 / 耦合         │
│ 接触参数       │ 振动可视化        │ 房间 / 输出 / 止音  │
├ 底栏：键盘（可用键高亮、已校准键标记）                 ┤
└ 状态行：校准状态、可演奏范围、延迟、采样率             ┘
```

不同乐器族只改变每个区域里放什么。手碟和舌鼓的激励是奏法、击打位置、接触硬度；小提琴是奏法、弓压、弓速、接触点 β；将来的拨弦乐器可以是拨片位置、拨片硬度；管乐是气压、唇压或簧片刚度。舞台由各乐器自己的渲染模块负责，右栏统一为“发声之后还在响的东西”。状态行坚持诚实原则：没有实测校准的型号就明确写“使用声学先验，尚未校准”。

## 技术路线：原生绘制 vs WebView

| | JUCE 原生（LookAndFeel + Component） | JUCE WebView（HTML/CSS/JS） |
|---|---|---|
| 设计到代码 | 设计稿需要手工翻译成 C++ 绘制代码 | 交互稿里的 CSS 变量和组件可直接沿用 |
| 主题与系列化 | 自建 token 系统，可行但改起来慢 | CSS 变量天然支持，换主题即换一个文件 |
| 迭代速度 | 每次改动重新编译插件 | 可连开发服务器热重载，不重编插件 |
| 依赖 | 无 | Windows 依赖 WebView2（Win11 自带）；macOS 用系统 WebKit |
| 性能 | 最稳 | 界面加载和日常交互接近原生；大数据量推送需注意 |
| 宿主兼容 | 最成熟 | 需要在 Studio One / Ableton 中实测焦点、键盘、鼠标捕获 |

JUCE 9.0.2 已经具备完整的 WebView 参数桥接：`WebSliderRelay` / `WebToggleButtonRelay` / `WebComboBoxRelay` 在 C++ 端代表一个控件，配合 `WebSliderParameterAttachment` 等与 APVTS 参数双向绑定；前端通过 JUCE 自带的 `webview-interop` 包中的 `getSliderState` / `getComboBoxState` 读写；`Options::withResourceProvider` 可把打包好的前端文件从 BinaryData 提供给页面，插件不依赖外部文件；`JUCE_USE_WIN_WEBVIEW2_WITH_STATIC_LINKING` 可静态链接 WebView2 加载器。官方示例在 `JUCE-9.0.2/examples/Plugins/WebViewPluginDemo.h`。

已知风险和应对：社区反馈 `emitEvent` 传大对象时 JSON 序列化很慢，所以舞台可视化不传音频，只传“发声事件”（音区、音高、力度、分音频率与衰减时间），由前端自己画衰减；电平表以 30 Hz 推送一个数字即可。拖动旋钮或滑块时鼠标离开插件窗口的问题，需要用 `setPointerCapture` 处理并在你的两个 DAW 中实测。JUCE 论坛的建议是界面要么全 WebView、要么全原生，不要混用多个浏览器组件。

如果实测发现 WebView 在你的目标宿主里有无法接受的问题，退路也清楚：保留同一份 token（颜色、字号、间距、圆角）作为 JSON，由 C++ 端的 LookAndFeel 读取，骨架和组件名一一对应，设计语言不需要重做。

## 前端引擎结构

建议把前端拆成与乐器无关的“核心”和与乐器有关的“舞台”两部分：

```
ui/
  core/          骨架布局、滑块、奏法列表、键盘、电平、状态行、JUCE 桥接
  themes/        nodal.css（手碟）/ calibre.css（舌鼓），只有 CSS 变量和少量组件覆盖
  stages/        handpan.js / tongue.js / violin.js（各自实现 init / onVoice / draw）
  index.html     读取 manifest，组装界面
```

C++ 端在加载时向前端发送一份 manifest，内容由 `ModelRegistry.h` 生成，前端据此决定显示哪些控件、哪些键可用、哪些键已校准：

```json
{
  "family": "handpan",
  "theme": "nodal",
  "model": { "id": "somera", "name": "Somera" },
  "articulations": ["Finger Whacks", "Fingertip / Slap", "Thumb Whacks", "Knuckle", "Muted", "Mallet"],
  "controls": {
    "exciter": [{ "param": "position", "label": "Strike position" }, { "param": "hardness", "label": "Contact hardness" }],
    "body":    [{ "param": "gain", "label": "Output" }]
  },
  "keys": { "playable": [50,57,58,60,62,64,65,69,72], "calibrated": [62] },
  "stage": "handpan-9"
}
```

参数 ID 继续由 C++ 端定义并保持稳定（现在的 `model` / `articulation` / `gain` / `position` / `hardness`），前端只通过 ID 引用，不依赖顺序。这一点和现有的“宿主型号 ID 不因界面顺序改变”约定一致。新乐器接入系列时，只需要新增一个 manifest 和一个舞台模块，核心与主题不动。
